## Real semantic conflicts repaired in the isolated direct OpenAI factory

1. Previous merging erased earlier headers when a later value was undefined. SDK undefined values are skipped; null deletes and retains its tombstone.
2. Previous plain-record string conversion bypassed Headers validation, trimming and array append semantics. The new bounded native SDK header helper uses actual Headers and Set objects and follows the pinned merge loops. Its scope is this client's non-branded sources; private SDK-branded nullable wrapper interop is not claimed.
3. JSON body content-type now applies after client defaultHeaders, as the primary SDK encoder requires. Request-level header precedence is exercised in the helper controls, although Pi's current OpenAI requestOptions do not supply request headers.

## Shared HTTP protocol proposal — not implemented

Pinned Zig0.16 `std.http.Client.Request.Headers` exposes typed `.default`, `.omit`, `.override` fields for host, authorization, user_agent, connection, accept_encoding and content_type. Its sendHead emits those fields, then generated transfer encoding, then all extra_headers verbatim. Current shared fetchObserved suppresses only a duplicate User-Agent. Current Worker passes keep_alive=false and extra_headers; custom Host, connection or encoding can therefore duplicate a standard field. No shared HTTP worker or fetch helper changed.

The concrete proposed next patch is an opt-in, reviewed SDK fixed-body profile after effective prepared-header merging. Route validated standard-header overrides through the typed Request.Headers API and remove their duplicate extra-header entries. Leave qualified other callers on the current default until their contracts are reviewed. Caller-provided Host must produce exactly one header; the URI still selects the actual network destination. Source Node7.21 also derives a servername from custom Host in its request path, so TLS/SNI equivalence requires separate explicit review and a genuine controlled TLS case before any claim or behavior change.

There is no typed content-length override field. Keep transfer_encoding.content_length tied to the actual payload byte count. A supplied content-length requires primary-compatible parsing/validation, mismatch rejection and suppression of an additional emitted field; never send two lengths, or a length plus caller transfer-encoding. The captured actual bundled Undici7.21 primary source (SHA C62030F1E505A4010D9972ECBF40155EDDEB355F2A53A9F019A447214E1A9600) parses request content length at3077, checks fixed-body mismatch before writing at7731, and writes computed buffer-body length at7916. The installed npm undici8.10.2 is a different dependency and is not used as Node's bundled-fetch authority.

The same actual7.21 source accepts connection only close/keep-alive, rejects caller transfer-encoding/keep-alive/upgrade, and rejects expect as unsupported at3084-3098. A shared patch must preserve these error boundaries and the native connection lifetime rather than merely copying conflicting bytes. Explicit accept-encoding must not advertise a coding the selected native response decoder cannot handle; its exact user-override behavior and errors need a genuine Source control before implementation. Default native connection close is protocol-valid and explicit, and remains distinct from the original Node keep-alive record; it is not classified as runtime identity.

This proposal does not authorize removing arbitrary headers or relaxing the original full58 payload, callback, event, producer identity, retry, JSON/deep or thinking DROP checks.
