## Actual missing API

The verified C3 header exports JS_PiNewNativeAsyncGenerator (an INSTANCE), JS_PiGetAsyncGeneratorPrototype and JS_PiGetAsyncGeneratorFunctionPrototype. It does not export a native generator-FUNCTION factory. Existing EventStream used ordinary createMethod plus prototype assignment. The new consumer requires the explicit proposed JS_PiNewNativeAsyncGeneratorFunction API; it does not claim that C3 already provides it.

proposed-c-api.patch is INERT, apply-check only. It introduces explicit native factory/resume members in the real JSFunctionBytecode representation and uses existing js_closure to create the actual JS_CLASS_ASYNC_GENERATOR_FUNCTION, name/length and own prototype. It retains the real bytecode GC/finalizer, constant pool and creation realm. Ordinary compiled/read functions keep zero native members. Metadata consumers exclude both native variants from bytecode PCs/source and serialization; toString remains truthful native code. Calls capture state without entering the generator body, then use the VM's js_create_from_ctor prototype lookup/realm fallback and attach the existing C3 native generator data/queue. There is no forwarding yield*, wrapper Await, generated user code or fake kind flag.

The callback borrows receiver/arguments/captures and returns owned captured state. Its returned owner is retained/marked by the existing generator until retirement. Exception callbacks obey the actual C API convention. Pending entry does no callback work; pending output ownership uses a local take-clear-drain restoring the first actual fatal reason. This does not undo guest work inside a deliberately contract-violating native callback. The patch does not alter the original instance API/queue algorithms. The C proposal requires independent review, Root authorization, composition and actual qualification before selection.

## Actual Zig implementation

native_async_generator_function.zig retains/traces native factory captures and binds the proposed exact C ABI. EventStream constructor now requests that actual generator function rather than assigning an AsyncGeneratorFunction prototype to an ordinary function. Existing host iterator entry still uses the real C3 instance API and shares the same private owner constructor/body. The owner is private null-prototype state; public Source fields and FIFO body remain unchanged.

native_promise_executor_fatal.zig is an independent per-construction native holder, following closed Agent fc2 ownership. Both final-result and waiting Promise executors capture this holder. Every failed setter/getter/call is classified against its own operation generation, not callback-start; a getter's caught native history therefore cannot become fresh at a later call. It records the first exact direct host allocator/fresh private failure, without allocation in the retention step. Actual constructor success, later ordinary throw or later diagnostic/OOM cannot replace that retained reason. Historical private reasons and marked untagged data do not become new events. It drains displaced owned values with mutable slots cleared, and uses the existing diagnostics suppression while moving errors without invoking guest ToString.

## Explicit remaining C3 producer-exit negative

Leaf retention fixes the actual Promise boundary; it does NOT alone fix delivery from the generator. Current C3 js_native_async_generator_drive consumes JS_EXCEPTION through JS_GetException, completes the generator, calls js_async_generator_reject and frees the reason. js_async_generator_next then returns its Promise, and the reaction callback similarly returns undefined after driving. Thus an actual pending marked executor failure can still become rejection DATA in the waiting path. This is a separate concrete C3 producer-exit correction, documented in PRODUCER-EXIT.md; no positive host-fatal generator claim is made. Do not infer fatal from a bit on arbitrary rejected DATA.
