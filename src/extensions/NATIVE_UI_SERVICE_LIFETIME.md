# Retained native Main UI services

This isolated follow-on is based on Root composition `1a90ca5`. It is development source until a frozen four-configuration receipt is published. It does not promote the native backend or remove the JS/TS compatibility bridge.

Actual Source captures `main-ui-service-source-349b`, `349c`, `main-ui-service-siblings-source-356`, and `main-ui-service-stale-sdk-source-358` establish the boundary: a previously obtained raw Main UI continues using its original frontend after the Main command returns, from an idle timer, after session reload, and after AgentSession disposal. A fresh UI after frontend rebinding uses the new frontend. An explicitly retained raw Main UI can also be called from a disposed SDK event, while that event's SDK ctx/Pi remain canonically stale before and after the UI await. The raw service belongs to its frontend Runtime lifetime; removing its originating extension is not the service's retirement boundary.

The implementation issues services only from an actual native Main Binding. Its original native owner token/class and provenance remain part of the opaque service record. SDK private owners and provider-ticket contexts cannot issue Main service leases. Ordinary context JSON and public fields on a UI object cannot establish ownership. After issuance, the raw service validates its stored native token and actual Manager/Runtime owner generation independently of the originating Pi Binding. Pi and ctx guards continue to validate their original Binding and SDK leases.

Each service retains its own `Manager.InvocationState`: pending dialogs, generation, custom components, viewport and close protocol. A service call, response, control, abort callback or component callback exchanges only this state into the shared UI manager, then restores it. It never clears or changes the native async execution token. The frontend uses UI owner zero, separate from positive Main and descending SDK registration IDs, so removing an extension still retires that extension's original editor/widget/provider scopes. Persistent frontend editor/widget/theme state stays shared. The frontend Manager owns service records until Runtime shutdown and closes their pending work before its own destruction.

The Main ctx.ui getter reads the current shared frontend object only after the original context and owner guards succeed. It does not keep an old frontend object in a stale context. Headless Main contexts share the existing exact Source no-op UI singleton. UI wrappers derive their methods from the actual native UI method enum, so a newly implemented native UI method inherits the service lease without another method list.

The parent sends a private FIFO `native_ui_service_epoch` control before an ordinary invocation when its UiBridge revision changes. Version, Runtime owner generation and monotonic control ID are checked on the VM thread. The service generation identifies the original frontend, including when an earlier frontend is restored after a temporary bridge. A newer control drops the shared current UI object, while explicitly retained older objects keep their original service. This control is distinct from public context JSON.

Private service notices carry version, ownerGeneration, extensionId, serviceId and serviceGeneration. Requests and controls add requestId. Service-open is accepted only against the parent's current original invocation and extension identities and pins that original UiBridge. Requests run in bounded owned native callback tasks outside Runtime.mutex. Cancellation matches the entire request tuple and joins only that task; cancellation protection remains active until its memory is released. Runtime shutdown cancels and joins all outstanding callbacks. The existing persistent stdout reader dispatches service records alongside catalog ACKs, context invalidations, metadata, widgets, editors and renderers; there is no competing pipe reader.

Responses are applied only by the VM thread. The actual native service and pending request are found before allocating a guest value. Foreign owner, service, generation, extension and request identities are ignored; completed IDs cannot be replayed into a later promise. Frontend failures become ordinary VM Error objects. Custom-component scenes, mouse outcomes, controls and close acknowledgements carry both the private request tuple and their existing component fence. Native component handles retain and mark their opaque service token and release it with RT-only finalization. An asynchronous factory, done or redraw callback activates the original service before looking up its native handle, while preserving the original SDK or provider execution token.

Development receipts currently cover real no-Node workers for completed Main/idle/UI-rebinding behavior, two admitted held requests with one abort and the sibling preserved, valid/rejected catalog ACKs while an ordinary callback awaits its dialog, extension removal with raw frontend retention, Runtime shutdown cancellation, an actual disposed-SDK event, and asynchronous custom factory/render/input/original-error/close/disposal behavior. Actual VM controls reject foreign tuples and replay while a genuine request is pending. Source custom-component capture uses the actual Runner with a supplied embedding frontend driver; it does not claim physical interactive-terminal certification.

The exhaustive allocation target uses `test_support/sdk_allocation_shards.zig`. By default it exercises every failure index; hosted jobs may set `PI_SDK_ALLOCATION_SHARD=0..7` and `PI_SDK_ALLOCATION_SHARDS=8`, and all eight ranges are required for complete coverage. VM-side class, wrapper, signal, component, control and retirement allocations are covered. Parent callback tasks deliberately use the existing thread-safe page allocator; their admission/cancel/join/close behavior is exercised by process tests, and this packet does not claim exhaustive page-allocation fault injection.

Broader UI and SDK parity remains separately gated. In particular, the real Main UI facade still needs getAllThemes/getTheme/setTheme/getToolsExpanded/setToolsExpanded wiring, and the separately discovered shared-loader SDK disposal invalidation is owned by the resource-owner lane. Native default promotion remains false.
