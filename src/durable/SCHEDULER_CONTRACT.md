## Implemented behavior

`task_state.zig` validates native durable task records and walks the task/conversation ownership graph, including settled task nodes. `scheduler.zig` owns cloned native task definitions and retained callback resources. A definition contains named phase functions, an abort function, an optional initial function and migration function, and a positive version. JSON inputs/checkpoints/outcomes use the existing lossless native JSON layer.

Session task creation validates the actual conversation, child ownership, background restrictions, and conversation inheritance before invoking a definition's initial callback. IDs are minted after that callback succeeds. Replacement rejects committed terminal tasks, terminal candidates, and conversation changes. Assembly checks new owned work against the owner's final candidate: completing, terminal, or abort-marked owners cannot acquire new work. Multiple candidate writes to the same task coalesce. Terminal settlement retires task documents in the same storage commit, including newly created documents.

`Scheduler.open` recovers persisted running checkpoints to pending without starting handlers and reconciles crash-left cancellation marks and held outcomes. `enable` permits dispatch. `drive` reserves at most `max_workers` tasks on the serialized Session line, captures one definition snapshot for the whole reservation pass, starts actual native threads, joins those threads, then reconciles. `runUntilBlocked` drives up to a caller-supplied batch bound. Concurrent drive calls are rejected. Worker count is bounded to 1–64; phase steps have a configurable positive limit. The caller's allocator must support concurrent allocation when multiple worker threads are enabled.

Every runtime commit checks the invocation fence inside the Session callback, re-reads the current task, rejects a run invocation with a durable abort mark, and permits only running, waiting, or terminal next states. Retained runtimes reject after invocation end. A phase's committed terminal/waiting/completing state takes precedence over a later handler error; close and abort marks take precedence over a late error. Returning without checkpoint progress faults the task. Compatible replacement definitions take over only after durable progress. Failed migration is retried only after a different registered definition resolves the task.

Ordinary owned work holds a terminal outcome as completing. Finalization repeats until newly freed owners can settle. Cancellation marks propagate through task-owned conversations, stop at background boundaries, and run abort handlers bottom-up. An abort handler receives a fresh cancellation context and cannot wait. A waiting task may name existing tasks other than itself or its owners; failFast waits require directly owned members. Failed failFast members mark surviving members, while allSettled waits do not. Abort marks ignore an unrelated waiting set and wait only for ordinary owned work. Root/conversation idle checks retain settled background ownership boundaries.

Optional cleanup and queued-input withdrawal callbacks run in the durable Session transaction. Scheduler-written faulted/orphaned cleanup occurs when an outcome becomes terminal. Withdrawal visits only conversations with queued submissions in the reached scope. These callbacks are native functions; callers must stage durable effects through the supplied transaction. Arbitrary external side effects cannot be rolled back.

Session close observers are allocated at subscription time and run once outside the Session lock. An observer can reenter Session APIs or remove later observers. Off-line unsubscribe waits for an in-flight close notification. Closing inside a transaction dispatches observers after that transaction leaves the mutation line. Scheduler close seals admission and cancels active handler contexts. Native handlers must cooperate with their context for bounded join latency. The owner must join drive calls and release retained runtimes before destroying the scheduler; the scheduler must be destroyed before its Session/backend.

## Evidence and limits

`fixtures/scheduler_b7df.json` is data captured by executing the actual upstream TaskScheduler, SessionImpl, createRegistry, defineTask, and MemoryStorage under Node 24.14.0. It records eight scenarios: completion, no progress, original handler error, committed terminal state followed by error, waiting on self, abort, ownership cascade, and pre-resume running recovery. Native tests compare complete persisted records for every scenario (including three cascade records). Exception messages from upstream are preserved in the captured data; the native callback interface uses Zig `anyerror` values and exposes typed errors to its caller.

Additional tests exercise real simultaneous four-thread phases, running abort/late writes, migration failure caching and handover, failFast/allSettled behavior, task-document retirement, SQLite writer fencing, Session close during active work, resource retention/reentrant registration, and allocation failures. A repository-native fixture process exits with code 86 from its real phase handler immediately after SQLite reservation. The parent reopens that database, verifies the running checkpoint, recovers it to pending, and completes it exactly once.

Dispatch is explicitly driven. `abort` and `abortConversation` persist marks and reconcile; they do not wait for all handlers or scope idleness as the upstream asynchronous methods do. The driving owner supplies that join/idle policy. No automatic event-loop dispatcher, registry-uninstall bridge, or replacement-warning callback is included in this increment. Registry definitions remain retained until scheduler destruction so old invocations keep valid callbacks. Completed invocation allocations are reclaimed at the next drive unless a caller retains a runtime.

The full runtime facade (`agent`, model/environment resolution, hook execution, memo/sleep/document watches/snapshot forwarding), generation/tool/compaction task definitions, and binding user-authored extension task functions through QuickJS remain subsequent integration work. Existing Harness registry metadata and the new executable task registry are separate native APIs. This increment does not alter the legacy JSONL/SQLite session schema or claim upstream SQLite file-format compatibility. Ownership walks use complete detached snapshots and reject cycles/missing nodes; they prioritize correctness over the upstream cache's scaling behavior. The inherited filesystem/shell/watch support limits remain as documented in the frozen foundation.
